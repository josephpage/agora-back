## Kotlin behaviours reproduced on purpose (class A, found with the scenarios)

* A JSON `null` element in the list of `usersID` / `userIDsToDelete` is a 500 for the three routes, with no change (`String.toUuidOrNull()` receives null: NullPointerException). `null` as the whole list is a 400.
* Numbers and booleans in the list are strings (`[1]`, `[true]`: Jackson coerces them): an invalid id, `0 utilisateurs promus sur 1`, status 200. An object or a list in the list is a 400.
* `UUID.fromString` is lenient: an upper-case id and an abbreviated one (`0-0-4000-9000-3`) are the same user (`S10-body-upgrade-mixed`).
* The count of the upgrade / downgrade is the number of rows the `UPDATE` touched: a user already at the level counts, a duplicate counts once, an unknown or malformed id counts 0 (`S10-body-upgrade-duplicates`, `S10-upgrade-already-publisher-counts`).
* `force_question_selection` is a Spring Boolean with a default: absent or a single empty value → `false`; the first value decides (`…&…=abc` → 400); a blank text (`%20`) is a 400, not a null (`S10-access-weekly-tasks-roles`). `on` and `TRUE` are true (probed; `S10-admin-weekly-run-pending-s7`, pending S7).
* The admin routes answer 401 to an anonymous or bad-token caller and 403 to every other role, whatever the body (the security rule runs before the body is read): `S10-access-cross-*`.
* A deleted user's token is a 401 right after the deletion (the cache entry is evicted by both sides).
* `POST /admin/cache/clear` is FLUSHDB on the reference, which drops every Kotlin cache entry, the user cache of the other users included (`S10-known-B1-stale-until-cache-clear`: the read after the clear shows the database's rights).
* `GET /admin/weekly-tasks` (no `POST`), `PUT /admin/delete_users`, `HEAD`: the Spring 405 (`S10-access-methods-and-paths`).
