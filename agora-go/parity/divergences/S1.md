# S1 divergences

No class C divergence. Class B only (Go fresher), none visible in a single-instance run of the parity scenarios.

## B1 - login no longer rewrites a stale cached user

Kotlin `updateUser` saved the whole cached `UserDTO` (`dto.copy(fcmToken, lastConnectionDate)`), i.e. the
`is_banned`, `authorization_level`, `created_date` and `password` values read up to one hour earlier. A ban set
by the nightly job (plain SQL, no cache eviction) or a level change was therefore silently reverted by the next
login of the user. Go (`users.Service.UpdateUser`) writes `fcm_token` and `last_connection_date` only and evicts
the cached principal. Identical whenever the Kotlin cache was fresh.

## B2 - user cache evictions Kotlin did not have

`ChangeAuthorizationLevel` and `FlagSuspiciousUsers` (nightly ban) evict the Go user cache (Kotlin kept stale
authorizations / ban flags for up to an hour). Go negative lookups are cached 5 s instead of 1 h (already
documented in `users.go`).

## B3 - profile and ask-date caches are per process

`profileCache` (1 h) and `demographicInfoAskDate` (5 min) keep the Kotlin TTLs but live in the Go L1 instead of
Redis. On one instance the behaviour is the Kotlin one, including the quirk where a profile update after
`POST /profile/departments` erases the departments (`S1-profile-stale-cache-quirk`). With several Go instances
the update only sees the stale entry when the same instance served the previous profile write; otherwise it
reads the database (fresher). In coexistence mode a Go write deletes the Kotlin keys it would have overwritten.

## Not divergences, but limits

* `featureFlags::*` values written by hand in exotic Jackson type-id forms are approximated
  (`["java.lang.Boolean", x]` handled; other `java.lang.*` / `java.util.*` typed values = "not true"; unknown
  class names = error). Nothing in the application writes them.
