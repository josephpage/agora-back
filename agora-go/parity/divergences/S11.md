# S11 divergences (ACME certificate renewal)

Slice S11 = `internal/modules/acme`: the public challenge route, the four admin routes, the ACME / Cloudflare stubs, the renewal use case and the
custom command `acmeCertificateRenewalTasks`. On every HTTP route and on the database rows the two backends are identical (scenarios, JVM oracle,
cross-reading of the rows in both directions, see `parity/ledger/S11.md`). The entries below are what remains: everything observable only on the
wire towards the certificate authority (CA) or Cloudflare, or on malformed answers from them.

Class A = identical but implemented differently, B = Go is only "fresher" or fails more cleanly, N = not observable by an HTTP client of the backend, C = accepted difference, to be validated by the product.

| id | class | Kotlin | Go | observable effect |
|---|---|---|---|---|
| C-S11-TIMEOUT | C | acme4j (`NetworkSettings`): 10 s connect + 10 s read timeout per socket read, no total deadline. `RestTemplate` (Cloudflare, ACME directory check): 10 s connect + 30 s read per socket read, no total deadline | the same per-read timeouts (`net.Dialer`, `ResponseHeaderTimeout`) **plus** a total deadline: 60 s per logical ACME operation (`caOperationTimeout`), 90 s per `RestClient` call (`restTotalTimeout`) | a CA or Cloudflare that trickles bytes (one every few seconds) can keep a Kotlin request open for ever; Go gives up after the total deadline (the renewal then fails like a read timeout: the use case's exception path, rows left as in the Kotlin failure path). | C-S11-CA-STRICT | C | acme4j 2.16 parses and validates the CA answers with its own rules | `golang.org/x/crypto/acme` is the protocol engine (directory, nonces, JWS, order / authorization / challenge reads, certificate download); only `newAccount` and `finalize` are signed by hand (`rawPost`) because the library cannot express acme4j's requests (see `ca_acme.go`) | the two libraries are not guaranteed to agree on **non conforming** CA answers: they were not compared exhaustively, only the RFC 8555 flow of the stubs was, with identical operation sequences in four pairings (acme4j <-> Go stub, Go <-> Kotlin stub, Go <-> Go stub, acme4j <-> Kotlin stub). ## Kotlin behaviours reproduced on purpose (checked on the reference by the scenarios, the oracle or the unit tests)

* `GET /.well-known/acme-challenge/{token}`: 200 `text/plain` with the stored key authorization, 404 with an empty body for an unknown token; public (no JWT needed, a bad JWT is still a 401), also when `ACME_ENABLED=false`
  (`S11-off-routes`). 41 request shapes are compared (special characters, encoded space / slash / percent, dot segments, `;x=1`, trailing slash, `mediaType`, `Accept`, HEAD, CORS, other methods).
* `/admin/**` needs `ADMIN_APIS` (anonymous 401, every other role 403, also for the stub admin routes): `S11-admin-access`, 6 roles x 7 operations plus method / negotiation / unknown-path variants.
* `POST /admin/acme/renew-certificate` answers 200 with the **plain text** `Traitement de renouvellement du certificat ACME exécuté avec succès` (also when `ACME_ENABLED=false`, the use case then does nothing);
  `POST /admin/acme/upload-certificate` answers 200 `Certificat enregistré avec succès avec le statut TO_DEPLOY` (request body = `AcmeCertificateUploadJson`, `expiresAt` a Jackson `LocalDateTime`: string with or without seconds / nanoseconds, or the
  `[y,m,d,h,mi(,s(,n))]` array; offsets, date only, numbers, objects are 400; 42 request shapes in `S11-upload-certificate`). An exception of a use case is the application's generic error response (the same on both sides).
* The two health routes answer the Kotlin `{"message": ...}` map when the interaction is disabled, the DTO otherwise; the directory URL is `serverUrl.trimEnd('/') + "/directory"` (`/stub/acme///` works, `S11-health-checks`).
* Renewal state machine (ported unit tests + `S11-renew-*`): `ACME_ENABLED` gate; the **latest certificate by `created_at`** decides (an older `DEPLOYED` is ignored; the status is read case sensitively: `deployed` or `FOO` is an exception);
  `TO_DEPLOY` is deployed without provisioning (a corrupted / non Base64 encrypted key fails at the decryption); provisioning when `expires_at` is less than 30 days away (exactly 30 days is **not**); an order older than 168 h (wall clock)
  is deleted and a new order started, a younger one is resumed (no account / no account URL: exception, nothing changes); a challenge timeout keeps the tokens and the order, a definitive error clears the tokens; `Retry-After` is
  tolerated while polling the challenge (polling goes on) and while polling the order (the status check of that round is skipped), and before the CSR it leaves the order flagged `ORDER_FINALIZING`.
* `ACME_SERVER_INTERACTION_ENABLED=false` skips the provisioning (a stored `TO_DEPLOY` certificate is still deployed); `ACME_CLOUDFLARE_INTERACTION_ENABLED=false` skips the deployment (the certificate stays `TO_DEPLOY`):
  `S11-gates-a-*`, `S11-gates-b-*`.
* The custom command `acmeCertificateRenewalTasks` does nothing unless `ACME_CRON_ENABLED=true` (the Kotlin handler logs and returns).
