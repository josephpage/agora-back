# S2 divergences

No class C divergence caused by S2 itself. The few differences that remain between the two backends on S2 routes come from the
foundations (request layer, JSON layer) and are listed under "Foundation findings" in `parity/ledger/S2.md`, with a skipped scenario each.

| id | class | Kotlin | Go | observable effect |
|---|---|---|---|---|
| B-USERFEEDBACK | B | after `POST /qags/{id}/feedback`, `InsertFeedbackQagUseCase` stores the PREVIOUS answer of the user in the `userFeedbackQags` cache (`null` = "not answered" for a first feedback) for one hour | the NEW answer is stored (the key is invalidated on every instance, the Kotlin key is deleted in coexistence mode) | Kotlin: the details of the QaG keep showing the old `feedbackUserResponse` (or none, and no `feedbackResults`, after a first feedback) for up to an hour; Go shows the answer just given. ## Behaviours that look like divergences but are the Kotlin ones (kept on purpose)

* `POST /qags/{id}/support` succeeds on the open QaG of another user (it is then not listed in the user's supports); the author of an accepted QaG may support it.
* A feedback is accepted for any `qagId` string (unknown QaG, not a UUID, uppercase variant = another key) and before the response exists.
* `POST /qags` does not check the thematique, has no feature flag, and the "FEATURE_DISABLED" ask status never happens.
* The details `responseDate` is the Strapi day at the current time of day.
* `thematique_id` / `qag_id` over 255 characters, an invalid status in the database, NULL columns mapped to non-null Kotlin properties: 500 (and, for the queued actions, a stuck lock on the Kotlin side).
* `GET /qags/{id}` of an open QaG by anyone but its author is a 404, even for a moderator; of a rejected QaG a 423 for everyone.
