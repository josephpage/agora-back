## Design notes

* **ACME client**: `golang.org/x/crypto/acme` does the protocol (directory, nonces, JWS RS256 / ES*, orders, authorizations, challenges, certificate download). Two requests are signed by hand with the same key because acme4j's requests cannot be expressed with the
  library: `newAccount` (acme4j always sends `termsOfServiceAgreed`, derives the EAB algorithm HS256 / HS384 / HS512 from the MAC key size, accepts 200 and 201 for `onlyReturnExisting`) and `finalize` (the library's `CreateOrderCert` waits and
  downloads; the use case needs the bare request and its own polling). The use case itself (`renewal.go`) is written against small interfaces (`CAProvider`, `CASession`, `CAAccount`, `CAOrder`, `CAAuthorization`, `CAChallenge`, `CACertificate`) that mirror what
  Kotlin calls on acme4j; it reproduces acme4j's object model (fresh `Authorization` / `Challenge` / `Certificate` objects per call, `update()` stores then raises `RetryAfterError`) because the state machine depends on it (stale challenge status after
  `authorization.update()`, two certificate downloads).
* **Interoperability of the rows** (the Kotlin and the Go backends can run on the same database): keys written as PKCS#1 `RSA PRIVATE KEY` PEM (BouncyCastle `JcaPEMWriter`), AES-256-GCM (12 byte IV | ciphertext | tag, standard Base64, key = Base64 of 32 bytes),
  `timestamp(6)` as wall-clock `LocalDateTime` (`wall()` for the 30 day / 168 h arithmetic).
* **Timeouts** (class C): per-read timeouts like acme4j (10 s / 10 s) and `RestTemplate` (10 s / 30 s), plus total deadlines 60 s / 90 s.
* **Concurrency**: the renewal is not guarded by a lock in Kotlin either (two simultaneous calls would both provision); Go does not add one, to keep the behaviour.

## Reproduced Kotlin quirks (checked on the reference)

See the end of `parity/divergences/S11.md` for the HTTP ones. State machine details covered by unit tests and scenarios: latest certificate by `created_at`; case sensitive status; `TO_DEPLOY` deployed without provisioning; threshold `< 30 days`;
168 h wall-clock stale order; resume of `CHALLENGE_PENDING` (tokens re-stored before `authorization.update()`, challenge re-triggered unless `PROCESSING`) and of `ORDER_FINALIZING` (poll, download, deploy); stale challenge object in the resume; `Retry-After`
asymmetry between challenge polling and order polling; pre-CSR `Retry-After` leaves `ORDER_FINALIZING`; timeout keeps the tokens, a definitive error clears them; certificate downloaded twice (second download only to read the leaf's `notAfter`).

## Foundation findings (nothing under `internal/{httpx,jsonjava,xmljava,cache,store,strapi,common,javacompat}` or `parity/runner` was modified)

1. **httpx: no helper for a raw `@RequestBody String`** (the ACME stub reads the JOSE body as a string and applies `consumes`): `stub.go` `stubBody` reads `c.Header("Content-Type")` / `c.R.Body` directly. A `c.RawBody()` plus a `consumes` check helper would remove that.
2. **Cross-module use of `content.LocalDateTime`** (S9's Jackson `LocalDateTime` reader) by the upload DTO: promote it to `internal/common` at integration (same remark as S3).
3. **xmljava: a nullable slice is omitted, whereas Kotlin writes `<lastDeployedAt/>` for a null `List` inside a `Map`** (`GET /admin/stub/acme/last-deploy?mediaType=xml`); worked around with a `*[]int` field (`xml:"lastDeployedAt,unwrapped"`), identical bytes for null and non-null checked against the reference.
4. **parity runner cannot normalise random columns**: encrypted keys / certificates (random IV, random keys), PEM chains and URLs that carry the port of each side differ between the two backends by construction, so the issuance scenarios use `dbdiff: none` / `body: status` / `compare.ignore` and the equivalent assertions
   are in the runner-free `parity_it_test.go`. A per-column "decrypt then compare" or "regexp" normaliser in the runner would let those scenarios compare the rows.
5. **run.sh extra env**: `PARITY_EXTRA_ENV_REF/GO` is used as a per-profile switch (five profiles for this slice); a restart of both applications is needed to change profile, so these scenarios cannot be in the default full run (they carry their own tags, `S11-off` is the only one that runs in the default profile).

## Open questions for the lead

1. **Total deadlines** (60 s per ACME operation, 90 s per Cloudflare / directory call) are class C: Kotlin has none. Say if you prefer to remove them (a trickling server could then hold a request for ever) or to change the values.
2. **Concurrent renewals**: the admin route and the cron command can run at the same time and both provision (Kotlin too). Do you want a PostgreSQL advisory lock around `RenewIfNeeded` (a class B improvement, one order at a time)?
3. **Stub in production**: `ACME_STUB_MODE=true` registers public `/stub/**` routes (as Kotlin does); nothing in this port protects against enabling it by mistake.
4. **Integration**: `internal/modules/acme` is already listed in `internal/modules/all/all.go`; it sets `tasks.AcmeRenewal` from its `init()` (the `TODO(S11)` comment and the default no-op in `internal/tasks/tasks.go` can be removed, that file is not mine).
