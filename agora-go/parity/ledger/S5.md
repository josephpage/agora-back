## For S6 (consultation responses): ONE thing to do, and it is automatic

After a user's answer, Kotlin's `InsertReponseConsultationUseCase` calls `consultationAnsweredPaginatedListCacheRepository.clearCache(userId)`.
In Go **S6 has nothing extra to call for this cache**: `consultation.Get(a).Answered.InsertUserAnsweredConsultation(ctx, answered.UserAnswered{...})` (the call S6
must make anyway, at the same place as Kotlin: after the response rows are inserted) runs the hooks registered by `consultationlist.Get(a)` once the row is committed, which evicts
the user's answered pages on every Go instance and, in coexistence mode, the Kotlin keys. `consultationlist.Get(a)` is built by `all.Routes` (`consultationlist.Routes`), so the hook is
registered in every web process. The only other call S6 makes is the one S4 already documented: `consultation.Get(a).EvictHasAnswered(ctx, consultationID, userID)`
(what Kotlin evicts for "has answered"). If S6 ever changes what a user answered **without** `InsertUserAnsweredConsultation` (a deletion, a direct SQL), call
`consultationlist.Get(a).EvictAnswered(ctx, userID)`.

## For S7 / S10 (daily task, admin)

`ConsultationCacheClearUseCase.clearConsultationCaches` also empties the finished pages: call **`consultationlist.Get(a).ClearConsultationCaches(ctx)`** (it builds the module, so the
hook that clears `consultationsFinishedPaginated` is registered even in the cron process, which never builds the routes) instead of `consultation.Get(a).ClearConsultationCaches(ctx)`.
The admin `POST /admin/cache/clear` (FLUSHDB) is handled by the cache foundation (epoch watcher clears every L1).
