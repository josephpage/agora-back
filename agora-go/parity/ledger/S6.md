## Exported API (for S10 and the other slices)

```go
s := consultationresponse.Get(a)   // *Service; consultationresponse.Routes(a) registers the three routes

s.AggregateConsultations(ctx) error                       // PickConsultationsToAggregateUseCase.aggregateConsultations: the DAILY TASK calls it
s.AggregateConsultationResults(ctx, consultationID) error // AggregateConsultationResultUseCase (one consultation)
s.DeleteUserConsultationResponses(ctx, userIDs) error     // GetConsultationResponseRepository.deleteUserConsultationResponses: DeleteUsersUseCase calls it
                                                          // (it drops every cached result, the counts change); an empty list after dropping the non UUIDs
                                                          // is an error, like the `IN ()` of Hibernate
s.EvictConsultationResults(ctx, consultationID)           // drop the cached results of one consultation on every instance (+ the Kotlin key in coexistence)
s.EvictAllConsultationResults(ctx)
```

* **Daily task (S10)**: call `consultationresponse.Get(a).AggregateConsultations(ctx)` where `DailyTasksHandler` calls `pickConsultationsToAggregateUseCase.aggregateConsultations()`.
  It uses `consultation.Get(a).Info.GetConsultationsToAggregate` (S4: the consultations that ended 14 days ago). The aggregation does not change the results (same counts),
  so it does not evict anything. An error stops the loop like a Kotlin exception.
* **DeleteUsers (S10)**: `consultationresponse.Get(a).DeleteUserConsultationResponses(ctx, ids)` (the answers of the users are deleted; `user_answered_consultation` is
  not touched by Kotlin either).
* An answer calls, in this order, `Answered.InsertUserAnsweredConsultation` (S4; its `OnInserted` hook evicts the answered pages of S5), `consultation.Get(a).EvictHasAnswered`
  (S4) and `EvictConsultationResults`; S5 needs nothing else.

Harness notes (nothing to chase, recorded for whoever re-runs S6):

* **Trigger on `reponses_consultation`.** The runner binds ONE generated UUID per pair of rows, so the rows of an answer, which share a random `participation_id` (different on each side), cannot be
  matched (see "Foundation findings"). The scenarios that write answers install, in `setup.sql`, a `BEFORE INSERT` trigger that replaces a non-zero `participation_id` by `md5(user_id || '/' || consultation_id)::uuid`
  for the rows written in the last 10 minutes. The DB diff therefore still checks that the rows of one answer share a participation id and that two answers do not. The trigger stays in the databases of the slot
  after the run (it never touches a seeded row, so the other slices are not affected); `DROP TRIGGER s6_participation ON reponses_consultation` removes it.
* The Kotlin in-JVM caches (Strapi, 5 min) and the `AgoraQueue` locks survive the per-scenario reset: `restart-ref` AND `restart-go` before a reproducible run. The 500 scenarios (`null` elements) use one dedicated
  user each (`UserMass1..7`, regular users never used elsewhere: the reference keeps their queue slot until it restarts).
* `{{seed.X}}` templates are **not** expanded in `setup.sql` / `setup.redis`: the SQL of the data scenarios uses literal ids. The rate limit counters preset in Redis use the IP hashes of `X-Forwarded-For: 10.7.0.N`
  (computed once through the backend: `REMOTE_ADDRESS_*` of `parity/env/common.env`).
* Consultation 3 of the fixtures ends 3 days after the pinned Strapi clock (2026-10-06) and is finished in real time: the answer scenarios use consultations 1 and 2 (and 6, unpublished) as the open ones.
* Users with a NULL `last_connection_date` (`UserNoFcm1`, the abuse groups) are 500 from their second request on both backends (cached `UserDTO`): they are used once per scenario.

## Foundation findings (nothing was modified in the foundation packages)

1. **`parity/runner` DB diff cannot bind a generated UUID shared by several rows of one table within a step.** `diffDB` pairs the unmatched rows of a table that differ only by unbound UUIDs, and
   `rowsBindable` refuses a pair as soon as one of its two UUIDs is already bound, even to the very value of the other side. Repro: any write that inserts two rows sharing a generated value, e.g.
   `POST /consultations/{id}/responses` (the rows of one answer share `participation_id`): the first pair is bound, the other rows are reported as `(missing)` / extra. Fix: in `rowsBindable`, accept
   `refToGo[r] == g` (and `goToRef[g] == r`). Worked around in the scenarios with the trigger described above.
2. **`{{seed.X}}` is not expanded in `setup.sql` and `setup.redis`** (only in steps): the SQL has to repeat the literal ids.
3. `Ctx.BindBody` (existing finding C-XML-BODY): `application/xml` bodies are refused; `S6-known-xml-request-body` (skipped).
4. `cache.DeleteKotlinPattern("consultationResults::*")` walks the keyspace with SCAN once per users deletion (coexistence only): fine.
5. `javacompat` has no `NumberFormat`/`DecimalFormat`: `numberformat.go` (JDK 17 `DigitList` algorithm, 7 languages) lives in this module; promote it if another slice needs it.
