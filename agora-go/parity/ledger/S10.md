## Custom commands and start-up

* `cmd/agora/main.go`: `tasks.LogFeatureFlags` runs right after `build` (FeatureFlagsLogger is a bean: it runs at the start-up of every process, the web server and each cron command). A flag that cannot be
  read (Redis) exits 1, as a Kotlin start-up failure does. Reading a flag also initializes its shared key `featureFlags::<NAME>` from the environment, as Kotlin does.
* `tasks.ParseCustomCommand(os.Args[1:])` (AgoraCustomCommandHelper): the FIRST argument starting with `--run-custom-command=`; the command is trimmed with Kotlin `trim()` (Unicode spaces included);
  a blank command is no custom command (the web server starts); the following arguments are joined with `\n` and split again on `\n` (an argument containing a newline yields several),
  blank pieces are dropped, `--key=value` pieces give the map (the last value of a key wins, the first `=` separates), other pieces are ignored. A second `--run-custom-command=` is a plain `--key=value` argument
  (`run-custom-command` key), as in Kotlin. The previous Go parser trimmed with `strings.TrimSpace` and did not split on newlines.
* `tasks.Handlers` maps `dailyTasks`, `weeklyTasks`, `acmeCertificateRenewalTasks` (S11 fills the last one). An unknown command exits 0, as Kotlin (`getHandler` null → `true`).
* `AGORA_CRON_DISABLED=true` (Go only, parallel app): the command returns 0 before the handler runs (unchanged).

## QaG lifecycle: the registration point for S7 (the lead)

`internal/tasks/weekly.go` declares

```go
type QagLifecycle interface {
    PutMostPopularQagInSelectedStatus(ctx context.Context) error // SelectMostPopularQagUseCase
    ArchiveOldQag(ctx context.Context) error                     // ArchiveOldQagUseCase
    AnonymizeOldQag(ctx context.Context) error                   // AnonymizeOldQagUseCase
}
func RegisterQagLifecycle(factory func(a *app.App) QagLifecycle)
```

S7 (moderatus) must call `tasks.RegisterQagLifecycle(func(a *app.App) tasks.QagLifecycle { return moderatus.Get(a) })` **during package initialization** (an `init()` in its package, or in `internal/modules/all`):
the cron process never builds the routes, so an explicit call in `all.Routes` would not run there. Until it is registered, `Weekly` logs an ERROR (`weeklyTasks: no QaG lifecycle is registered …`) and returns an error:
the admin route answers 500 and the cron exits 1. **Do not move the cron `weeklyTasks` of `cron.json` to the Go app before S7 is registered** (the Go task would do nothing but fail).
`Weekly` checks the factory before anything else, so a failing registration never runs a partial task.

### Reference quirks found by these scenarios (all reproduced; class A)

* `DELETE /admin/delete_users` with `["not-a-uuid"]` answers 200 and changes nothing (the reference runs the empty `IN` of the consultation response delete without error). The S6 function raises a syntax error for
  an empty list (`DELETE FROM reponses_consultation WHERE user_id IN ()`, 500). The admin call is skipped when no id is a UUID (`withUUIDsOnly`); the S6 module is not changed. See "Foundation findings" (S6).
* `[null]` in a request list is a 500 (NullPointerException of `String.toUuidOrNull()`), with no change, for the three routes (`null` elements are kept as `[]*string`).
* `?force_question_selection=` with a blank text (`%20`) is a 400 for the Boolean: `CustomBooleanEditor` rejects a blank text, it is not a null. With several values, the first one decides (`&force_question_selection=true` after `=` → 400).
* `usersID: [1]` and `[true]`: Jackson coerces the scalar to a String: an invalid id, `0 utilisateurs promus sur 1`.
* Upper-case and lenient UUIDs (`0-0-4000-9000-3`) are accepted, as `UUID.fromString` does.
* After the deletion of a user (cached or not) the same JWT is a 401.

### Reference quirk: the user cache keeps old rights (S10-B1)

The reference caches the `UserDTO` (with the authorization level) in `userCache` for an hour and does not evict it on upgrade or downgrade. A user who was authenticated before the change
keeps the old rights until the entry expires or the admin cache clear runs. Go invalidates the user at once. The scenarios avoid the window (every user changed by a scenario is first read after the change),
and `S10_known_divergences.yaml` documents the window (skipped). Measured on the reference: after `upgrade_users_to_publisher` of a user read before, `GET /consultations` still lists 1 ongoing consultation
(Go 2); after the downgrade of a publisher read before, it still lists 2 (Go 1); the admin clear makes the reference fresh (same answer as Go).

## How to compare the cron tasks

The scenario runner can run the custom commands on both sides: a step with `admin: {command: dailyTasks}` (or `weeklyTasks` with `args`) runs `start-ref.sh --run-custom-command=…` and
`start-go.sh --run-custom-command=…` against the seeded databases, then the DB diff of that step is taken like for an HTTP step (`S10_cron.yaml`).

Measured on slot 2 (the Kotlin jar in `/home/user/agora-ref/build/libs/agora-back-0.0.1.jar`): on the seeded data, `dailyTasks` twice gives **no DB diff and the same reads afterwards** on both sides.
The only difference is the **exit status**: the reference exits 1 after `dailyTasks` (checked twice; the same `SpringApplication.exit` path serves the other commands, not run here), Go exits 0 (see divergence S10-C1). The runner counts a difference of exit status as a `command` diff,
so the four cron scenarios are skipped (`skip:`, with the reason).

To run them and check the DB effects anyway: remove the `skip:` lines of `S10_cron.yaml` (or copy the file without them), then `PARITY_SLOT=2 ./parity/run.sh test -tags S10 -run cron -v`:
the only expected diffs are the `command` ones (`ref: exit status 1 …`, `go: <nil>`). Any other diff (a row, a status, a body) is a real difference.

The manual form, for the lead, on the two databases: `java -jar <ref jar> --run-custom-command=dailyTasks` with the reference environment (`/home/user/run/slot2/start-ref.sh --run-custom-command=dailyTasks`)
and `/home/user/run/slot2/start-go.sh --run-custom-command=dailyTasks` for Go, each followed by the same reads.

`weeklyTasks` cannot pass before S7: the Go side fails loudly (no QaG lifecycle) while the reference runs its QaG steps. Its four scenarios are skipped with the S7 reason.

## Foundation findings (nothing in the foundation packages was modified)

1. **The runner compares the exit status of the custom command steps** (`parity/runner/runner.go`, `if (e1 == nil) != (e2 == nil)`). The reference cron exits 1 (its Spring context is cancelled
   by `SpringApplication.exit` during the refresh: `BeanCreationException … ProxyCachingConfiguration` then `APPLICATION FAILED TO START`, after the handler finished). Repro: any step
   `{id: x, admin: {command: dailyTasks}}` in a scenario reports a `command` diff. Options for the lead: an opt-in flag on the admin step (`ignoreExitStatus: true`), or the decision of divergence S10-C1.
2. **The Strapi check cannot see a refetch**: `strapiDiff` compares the SET of URIs requested per scenario (`norm` into a map). A cache clear followed by the same request is the same set with or without a refetch.
   Repro: `S10-cache-clear-thematiques-again` passes whether or not Go calls Strapi again. Proposal: keep the request count per URI and step (the fake Strapi already logs every request) and compare counts per step.
   The Go side is covered by `TestClearCacheMakesTheStrapiPageFetchedAgain` (a counting fake Strapi), not by the harness.
3. `httpx.Ctx.ParamDefault` on a Boolean: not used. A blank value of a Boolean with a default value is a 400 on the reference (the Spring `CustomBooleanEditor`), unlike an enum (S8, null → NPE). Worth a line in
   CONVENTIONS section 3 (the conversion decides: Boolean → 400, enum → null). `admin/handlers.go` `boolParam` reproduces it.
4. `BindBody` with `[]*string` elements: a JSON `null` element is kept (a 500 in the handler), `1` and `true` become strings, an object is a 400 (all checked on the reference through `S10-bodies`).
