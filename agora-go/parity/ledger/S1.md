## Reproduced Kotlin quirks (all checked on the reference)

* A user whose `password`, `created_date` or `last_connection_date` is NULL: the first access works, the
  cached `UserDTO` cannot be deserialized afterwards, so **every following request (auth filter, login)
  is a 500 for one hour**; the first `/login` already inserted its `users_data` row (`S1-login-null-*`,
  `S1-users-null-columns`). NULL `fcm_token` / `is_banned` fail every time.
* `users_data` columns are `varchar(255)`: a longer User-Agent / fcmToken makes the insert fail (500) - for
  signup *after* the user row was committed (`S1-signup-rejections`, `S1-login-after-signup`).
* Header values are ISO-8859-1 decoded by Tomcat and several values of one header are joined with `,`
  (`login/handlers.go` `headerValue`; `Ctx.RequiredHeader` does neither).
* `POST /profile`: the profile cache (1 h) is only read by the update path; `POST /profile/departments` writes
  with native SQL and leaves that entry, so the next profile update erases the departments
  (`S1-profile-stale-cache-quirk`); the insert path deletes the ask dates.
* `featureFlags::<ENV>` shared keys: `true`/`false`, strings/numbers are "not true", JSON `null` and an empty
  value are a miss (re-initialized from the environment), `["java.lang.Boolean", x]` typed form, anything
  else (`[true]`, `{}`, `garbage`, `TRUE`) is a 500 (`S1-signup-flag-*`).
* `signupCount::<ipHash>/<userAgent>`: plain integer, 24 h, created by `IsSuspiciousActivity` only (from the
  history, an old day >= 10 wins), incremented by signups only when it exists
  (`login/integration_test.go`, sequence observed on the Kotlin reference: 10 → key 10, 11th signup → 11).
* Ask date: `LIMIT 1` without ordering, a new row on every ask, NULL `ask_date` = NPE, `yearOfBirth` parsed
  with Kotlin `toIntOrNull` (`+1990`, `0001990` ok; `" 1990"`, `1990.5`, overflow → null), codes matched
  exactly (`m` is not `M`), departments matched case-insensitively on the value, null element in the
  departments list = NPE 500 *after* the count and the previous elements are checked.
* `REQUIRED_*_VERSION` unset = NPE (500), `ERROR_TEXT_QAG_DISABLED` unset = NPE.

## Foundation findings (not touched)

1. `auth.JWT.Parse`: a signed token without `sub` is a Kotlin NPE (500) - Go answers 401.
2. `httpx.acceptForBodies` (415 `Accept`) is wrong for every endpoint; Spring sends
   `application/xml;charset=UTF-8, text/xml;charset=UTF-8, application/json, application/*+xml;charset=UTF-8, application/*+json`.
3. 405 `Allow` is joined with `", "` by Spring (httpx uses `","`); the method order of `Allow` for a path with
   several methods is not stable on the Kotlin side (two JVM runs gave different orders) and
   `optionsAllow` should put GET,HEAD first like Spring's `HttpOptionsHandler`.
4. 406 must not carry the handler's headers (`Set-Cookie` of `/login?mediaType=foo`) - already fixed on the lead's branch.
5. `Ctx.Header/RequiredHeader/OptionalHeader`: Tomcat decodes header bytes as ISO-8859-1 and Spring joins
   repeated header lines with `,`; worked around in `login/handlers.go`, every slice binding string headers
   (User-Agent, fcmToken, ...) is affected.
6. `jsonjava.Unmarshal`: duplicate property names keep the last value while Jackson fails on an earlier invalid
   one (`{"gender":["x"],"gender":"M"}` is a 400) and `{"loginToken":"x","loginToken":null}` is accepted by
   Jackson with a null; a lone UTF-16 surrogate (`"\ud83d"`) becomes U+FFFD; the UTF-8 BOM is not skipped
   (rewrite announced).
7. XML request bodies are unsupported (C-XML-BODY, known).
8. Runner: the Go L1 flush published after the Redis flush is asynchronous; a scenario that starts immediately
   can lose an L1 entry (seen once on `S1-users-null-columns`, passes when re-run) - the 50 ms wait fixes it.
